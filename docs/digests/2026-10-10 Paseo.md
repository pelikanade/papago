## TL;DR

- **Paseo** (paseo.sh, repo `getpaseo/paseo`, Apache-2.0, ~20k stars, one maintainer, Mohamed Boudra) is a *daemon plus clients* manager for coding agents. The daemon launches the real agent CLIs (Claude Code, Codex, OpenCode, Pi, OMP, Copilot/ACP agents, Antigravity, Muse Code) in workspaces and git worktrees, and streams them to a desktop app, mobile app, web app and the `paseo` CLI. It is not an agent itself.
- **Why `/api/agents` is 404:** the daemon has no REST agent API. Its HTTP surface is tiny: `/api/health`, `/api/status`, `/api/files/download`, `/mcp/agents`. All agent control is a **WebSocket at `/ws`** (JSON "session" messages after a `hello`). The agent tool catalog is also exposed over MCP (streamable HTTP, stateless) at **`POST /mcp/agents`**.
- **Auth:** one daemon "password" (bcrypt hash in `~/.paseo/config.json` → `daemon.auth.password`). Clients send the plaintext as `Authorization: Bearer <password>`. `PASEO_TOKEN` on the box is that password. `/api/health` is open. The WebSocket accepts the same header on the upgrade request.
- **Verified live from the box (read-only):** neko-sphere runs **daemon 0.11.0-beta.5**, listening on `0.0.0.0:6767`, relay off, **0 agents, 0 projects, 0 workspaces, 0 schedules, 0 terminals**. **All 8 providers (claude, codex, copilot, opencode, pi, omp, antigravity, muse) are `unavailable` and disabled because no agent CLI is on the daemon's PATH.** So `paseo run` would fail today until the CLIs are installed on that host.
- **Read-only access from the box that works today:** `curl -x http://localhost:1056 -H "Authorization: Bearer $PASEO_TOKEN" http://100.92.72.101:6767/api/status`, a small Node WebSocket probe (`/workspace/paseo-skill/scripts/paseo-ro.mjs`, allow-listed read-only requests), or the real CLI through a local TCP forwarder (`PASEO_PASSWORD="$PASEO_TOKEN" paseo --host 127.0.0.1:6768 ls --json`).
- **Noa's Pi MCP question (2026-10-03): answered.** Paseo 0.10.2 could not give Pi its Paseo MCP tools on Pi ≥ 0.99 (Pi's built-in MCP, no `pi-mcp-adapter`). Issue #5744 (opened 2026-09-30, "Installed Paseo 0.10.2 has the same gate") was fixed by PR #5762 (merged 2026-09-30) and shipped in **0.11.0** (changelog: "Fixed Pi agents on Pi 0.99 starting without Paseo's MCP servers when `pi-mcp-adapter` is not installed"). The neko-sphere daemon (0.11.0-beta.5, tagged 2026-10-05) is newer than the fix. Details in §9.
- **nstack as a Paseo plugin is plausible:** a plugin runs in a daemon subprocess, can hook `agent.turn_ended`, send follow-ups, answer permissions, inject MCP servers/env and pick worktree isolation. Alternatively Paseo Hub triggers on GitHub events, but Hub runs unattended only Claude/Codex/OpenCode (not Pi/OMP). See §10.

## 1. What it is

- **Product:** "the agentic development environment": run many coding agents at once, on any machine, from desk or phone. Free; no telemetry, no forced login. Code stays on the daemon host; agents talk to their own provider APIs. It uses each provider's own CLI/login and does not extract tokens.
- **Repo / licence:** `github.com/getpaseo/paseo` (TypeScript monorepo, 1154 open issues, 2387 forks on 2026-10-09). GitHub shows "NOASSERTION" because the LICENSE file has a preamble; the body is Apache-2.0 and the website says Apache 2.0. History (from commits/HN): MIT commit 2026-02-05, HN posts in spring say AGPL-3.0, "Update project licensing (#3944)" on 2026-08-27 → Apache-2.0. The ClaudeKit page still says AGPL-3.0 (stale).
- **Versions:** npm `@getpaseo/cli` latest = **0.11.2** (2026-10-09). Releases: 0.10.0 (09-28), 0.10.1 (09-29), 0.10.2 (09-29/30), 0.10.3 (10-02), 0.11.0-beta.1..5 (10-01..10-05), 0.11.0 (10-07), 0.11.1 (10-07), 0.11.2 (10-09). Repo `main` = 0.11.2.
- **Pricing/business:** FOSS core; "Paseo Hub" is a hosted (free tier) or self-hostable layer for team access and GitHub/Slack/Discord triggers. Maintainer on HN: the business, when it comes, is the convenience/team layer.
- **Providers:** custom implementations for Claude, Codex, OpenCode, Pi, OMP (Oh My Pi), Antigravity (`agy`), Muse Code; "many more" via ACP (Copilot, Cursor, Gemini via ACP, Amp, Cline, Factory Droid, …, ~40 listed). Custom providers can `extends` a built-in and override `command`/`env` in `config.json` (`agents.providers.<id>`).
- **Features:** workspaces and git worktrees (branch-off / checkout-branch / checkout-pr), terminals, workspace scripts/services (`paseo.json`) with per-branch proxy URLs, diffs + PR panel, voice (local STT/TTS by default), browser tools (opt-in), schedules (cron) and heartbeats, agent profiles, permissions queue, usage dashboard, plugin system and registry, TypeScript SDK, Hub.

## 2. Architecture

- **Daemon** (`packages/server`, Node ≥ 22): HTTP+WS server, AgentManager (lifecycle state machine, timeline with epochs/sequence numbers), file-backed JSON storage at `$PASEO_HOME/agents/` (default `~/.paseo`), provider adapters, MCP adapter, schedules, plugin runtime, optional outbound relay and Hub link.
- **Clients:** Expo app (iOS, Android, web; web build can be served by the daemon), Electron desktop (bundles a managed daemon), CLI (Commander), `@getpaseo/client` SDK. All speak the same WebSocket protocol (`packages/protocol`, Zod schemas, `WS_PROTOCOL_VERSION = 1`).
- **Transports:** direct TCP WebSocket (`ws://host:6767/ws`), Unix socket / Windows pipe, SSH tunnel (`ssh://user@host`, CLI/desktop), or E2EE relay (`relay.paseo.sh`, Curve25519 + NaCl box; QR/pairing offer; off by default for new homes). Tailscale is the documented way for direct remote access.
- **Agents:** each agent = a provider session in a workspace; has `parent` (subagent tree), labels, mode, model, thinking option, feature toggles, timeline, pending permissions.
- **Paseo tools for agents:** one transport-neutral catalog (`server/agent/tools/paseo-tools.ts`). MCP is the fallback adapter; providers with native tool support (e.g. OMP) get the catalog directly. Injection into launched agents is **off by default** (`daemon.mcp.injectIntoAgents=false`).
- **Docs site map (paseo.sh/docs):** Getting started (index, connectivity, Docker, security, updates, web UI, why), Workspaces (workspaces, worktrees, parallel development), Providers (providers, supported, Claude Code, Codex, custom, Muse Code), Orchestration (overview, common workflows, agent profiles, skills, MCP reference, CLI reference), Schedules (overview, CLI, chat), Configuration (config, voice, metadata generation), Browser, Plugins (quickstart, reference, providers, publishing, migration), TypeScript SDK (quickstart, agents, workspaces, providers, events, recipes, reference), Hub (quickstart, concepts, triggers, daemons, workflows, GitHub, security, API, self-hosting), Troubleshooting.

- **No `chat` or `loop` CLI commands in 0.11.2** (the WebSocket protocol still has `chat/*` and `loop/*` RPCs; unverified whether anything uses them). Old `paseo worktree` is a hidden compat alias.
- **Choosing a daemon:** `--home` (local supervisor home) or `--host` (explicit endpoint) or env `PASEO_HOME` / `PASEO_HOST`. Both set → `TARGET_AMBIGUOUS`. No default-port fallback: with neither set it uses the local `~/.paseo`. `--host` accepts `host:port`, `tcp://host:port?ssl=true&password=…`, `unix://path`, `ssh://user@host[:port][?daemonPort=n]`, or a relay pairing URL `https://app.paseo.sh/#offer=…`. Local-only commands (`start`, `daemon run`, `config`, `onboard`, `set-password`) reject `--host`.
- **CLI auth:** reads env **`PASEO_PASSWORD`** (not `PASEO_TOKEN`), or `password=` in a `tcp://` URI. On the same machine it falls back to a local credential file in `PASEO_HOME`. Errors: `AUTH_REQUIRED` ("Set PASEO_PASSWORD"), `AUTH_FAILED`.
- **Proxy:** the CLI uses `ws` with no proxy support. From this box use a TCP forwarder (§7).
- **Agent-scoped runs:** inside a Paseo agent `PASEO_AGENT_ID` makes `paseo run` create a *subagent* in the caller's workspace; `--workspace` re-places it.
- **Output:** `ls --json` returns a JSON array (`[]` when empty). `run` waits for completion by default; `--output-schema` prints only matching JSON.

## 5. Daemon HTTP and WebSocket API (from server source `bootstrap.ts`, `auth.ts`, `websocket-server.ts`, `protocol/messages.ts`)

**HTTP (express):** order is service-proxy → Host allowlist → CORS → `POST /api/terminal-activity` (token-gated, skips password) → optional web UI → **bearer-auth middleware** → routes.

| Route | Auth | Notes |
|---|---|---|
| `GET /api/health` | none | `{"status":"ok","timestamp":ISO}` |
| `GET /api/status` | bearer | `{"status":"server_info","serverId","hostname","version","listen"}` |
| `GET /api/files/download?token=` | self (one-time download token) | 400 without token, 403 invalid/expired |
| `POST/GET/DELETE /mcp/agents` | self: password bearer **or** per-run capability token | MCP; only POST works (GET/DELETE → 405) |
| `GET /public/*` | bearer | static assets |
| `POST /api/terminal-activity` | local token | do not call |
| everything else | bearer then 404 | e.g. `/api/agents`, `/mcp`, `/` (unless web UI enabled) |

Unknown paths without a bearer return **401 first**, not 404, because the auth middleware sits before routing.

**WebSocket `/ws`:**
1. Connect `ws://host:6767/ws`. Host header must pass the allowlist; Origin is only checked if present (absent Origin is fine).
2. Credential, either on the upgrade request (`Authorization: Bearer <password>`, or subprotocol `paseo.bearer.<password>`), or in the first frame `hello.auth = {"kind":"password","password":…}` (also `{"kind":"localCredential","token":…}`). With a password set and no credential, the hello is rejected with `hello.rejected` (`password_required`/`incorrect_password`/`incompatible_protocol`, `accepts:["password"]`).
3. First frame must be `{"type":"hello","clientId":"<unique>","clientType":"mobile|browser|cli|mcp|hub","protocolVersion":1,"appVersion":"…","capabilities":{…}}` (a hello timeout closes silent sockets).
4. Server answers `{"type":"session","message":{"type":"status","payload":{"status":"server_info","protocolVersion","serverId","hostname","version","permissions":[…],"desktopManaged","capabilities","features":{78 flags}}}}`.
5. Requests are `{"type":"session","message":{"type":"<name>","requestId":"…",…}}`; responses are `*_response` messages carrying the same `requestId`; failures arrive as `rpc_error {requestId, requestType, error, code}`. WS-level `ping`/`pong` exist.

**Session request types (names verified in `SessionInboundMessageSchema`; ~250 total, the useful ones):**

| Area | Request type |
|---|---|
| list/read agents | `fetch_agents_request` (`includeBackground`, `filter{labels,statuses,includeArchived,…}`, `page{limit≤200,cursor}`; `subscribe` opens a live subscription), `fetch_agent_request {agentId}` (id, unique prefix or exact title), `fetch_agent_history_request`, `fetch_agent_timeline_request {agentId, direction tail|before|after, cursor{epoch,seq}, limit}` |
| create/send/stop | `create_agent_request`, `agent.create.request` (newer shape with workspace placement; which of the two the CLI sends is unverified), `send_agent_message_request {agentId,text,images,activeTurnBehavior}`, `wait_for_finish_request {agentId,timeoutMs}`, `cancel_agent_request`, `archive_agent_request`, `delete_agent_request`, `resume_agent_request`, `refresh_agent_request`, `agent_permission_response {agentId,requestId,response}` |
| configure | `set_agent_mode_request`, `set_agent_model_request`, `set_agent_thinking_request`, `set_agent_feature_request`, `agent.config.apply.request`, `update_agent_request` (name, labels), `agent.detach.request` |
| workspaces | `workspace.create.request`, `fetch_workspaces_request`, `project.list.request`, `create_paseo_worktree_request`, `archive_workspace_request` |
| terminals | `list_terminals_request`, `create_terminal_request`, `capture_terminal_request`, `subscribe_terminal_request`, `terminal_input`, `kill_terminal_request` |
| providers | `get_providers_snapshot_request`, `list_available_providers_request`, `list_provider_models_request`, `provider_diagnostic_request {provider}` |
| daemon | `daemon.get_status.request`, `daemon.config.reload.request`, `get_daemon_config_request` (**contains the password hash; avoid**), `set_daemon_config_request`, `shutdown_server_request`, `restart_server_request`, `daemon.update.request` |
| schedules/loops/chat | `schedule/create|list|inspect|logs|pause|resume|delete|run-once|update`, `loop/run|list|inspect|logs|stop`, `chat/create|list|inspect|delete|post|read|wait` |

Live updates (`agent_update`, timeline items, terminal frames) only flow after a subscription (`fetch_agents_request.subscribe`, `agent.timeline.set_subscription.request`, `subscribe_terminal_request`). A plain `fetch_agents_request` is a one-shot read. **`fetch_agent_timeline_request` calls `ensureAgentLoaded`, which resumes a stored (closed) agent's provider session, so it is not purely read-only for closed agents.**

**SDK:** `@getpaseo/client` wraps all this: `createPaseoClient({url:"ws://host:6767/ws", password})`, `agents.list/create/ref`, `agent.send/run/waitForFinish/refresh/archive`, `workspaces.*`, `providers.*`, `config.get/patch`. `waitForFinish` defaults to a 10 minute deadline and returns `idle|permission|error|timeout`. `authHeader` option for proxies.

## 6. MCP server (`POST /mcp/agents`, streamable HTTP, **stateless**, no session id)

- Enabled by `daemon.mcp.enabled` (default true). Auth = daemon password bearer (or the per-run capability token the daemon injects into agents it launches). Optional `?callerAgentId=<id>` makes the call agent-scoped (subagent defaults, finish notifications). With no caller it is a *top-level* caller: `create_agent` without `workspaceId` makes a new local workspace; `notifyOnFinish` defaults false.
- Standard MCP: send JSON-RPC (`initialize`, `tools/list`, `tools/call`) as POST with `Accept: application/json, text/event-stream`. **Not tested live** (POST is outside the read-only rule); the 405 on GET is verified.
- **Tool names (verified from `registerTool` in `paseo-tools.ts`, 0.11.2 main):**
  - Agents: `create_agent`, `send_agent_prompt`, `get_agent_status`, `list_agents`, `cancel_agent`, `archive_agent`, `kill_agent`, `update_agent`, `get_agent_activity`, `set_agent_mode`.
  - Workspaces: `create_workspace`, `list_workspaces`, `rename_workspace`, `archive_workspace`; scripts: `list_workspace_scripts`, `start_workspace_script`, `stop_workspace_script`.
  - Terminals: `list_terminals`, `create_terminal`, `kill_terminal`, `capture_terminal`, `send_terminal_keys`.
  - Schedules/heartbeats: `create_schedule`, `list_schedules`, `inspect_schedule`, `pause_schedule`, `resume_schedule`, `update_schedule`, `schedule_logs`, `run_schedule_once`, `delete_schedule`, `create_heartbeat`, `delete_heartbeat`.
  - Providers/profiles/permissions: `list_providers`, `list_models`, `inspect_provider`, `list_profiles`, `list_pending_permissions`, `respond_to_permission`. Browser tools (opt-in) and voice `speak` are extra.
  - **There is no `wait_for_agent` MCP tool** (a docs line mentions it for OMP, but `registerTool` has none). Waiting = notification to a calling agent (`notifyOnFinish`), or poll `get_agent_status`/`get_agent_activity`, or use the WS `wait_for_finish_request` / SDK / `paseo wait`.
- **Key schemas:**
  - `create_agent`: `title` (≤ 60 chars, required), `provider` (`provider/model`, e.g. `codex/gpt-5.4`, required), `initialPrompt` (required), optional `workspaceId`, `labels{}`, `settings{modeId,thinkingOptionId,features}`, `notifyOnFinish`. Returns `{agentId,type,status,cwd,workspaceId,currentModeId,availableModes,guidance}` without waiting.
  - `send_agent_prompt`: `agentId`, `prompt`, optional `sessionMode`, `notifyOnFinish`. Returns `{success,disposition turn_started|out_of_band,status}`.
  - `get_agent_status {agentId}` → `{status,snapshot}`. `list_agents`: `includeBackground`, `includeArchived`, `cwd`, `sinceHours` (48), `statuses[]`, `limit` (50, ≤200). `get_agent_activity {agentId, limit?}` → `{agentId,updateCount,currentModeId,content}` (curated text).
  - `create_workspace`: `isolation local|worktree`, `path`, `projectId`, `title`, `background`, `mode branch-off|checkout-branch|checkout-pr`, `worktreeSlug`, `branchName`, `baseBranch`, `branch`, `prNumber`.
  - `create_schedule`: `prompt`, `cron`, `timezone`, `name`, `provider`, `cwd`, `isolation`, `maxRuns`, `expiresIn`.
- **Per-provider policy:** `agents.providers.<id>.paseoTools = {enabled, disabledTools[]}` limits the catalog (e.g. strip `create_agent`, `send_agent_prompt`, `kill_agent` from workers). It is not a security boundary against shell access. Not inherited through `extends`.

## 7. Auth, config and pitfalls

- **Config file:** `$PASEO_HOME/config.json` (default `~/.paseo`). Key fields: `daemon.listen`, `daemon.hostnames`, `daemon.cors.allowedOrigins`, `daemon.auth.password` (bcrypt hash), `daemon.relay.*`, `daemon.mcp.{enabled,injectIntoAgents}`, `agents.providers.<id>.{command,env,options,extends,paseoTools}`, `pluginsEnabled`. Env overrides on foreground/Docker runs: `PASEO_LISTEN`, `PASEO_PASSWORD` (plaintext, hashed at start), `PASEO_HOSTNAMES`, `PASEO_RELAY_ENABLED`, `PASEO_HOME`. `paseo reload` applies runtime-safe edits; listen address, auth, relay endpoint, logging need a restart. `paseo daemon set-password` needs a TTY.
- **Host allowlist (DNS-rebinding guard):** `daemon.hostnames` default `[]` = `localhost`, `*.localhost`, **all IP addresses**. A DNS name (e.g. a `.ts.net` name) must be listed (`".example.com"` allows subdomains; `true` = any). Rejection: HTTP 403 `{"error":"Invalid Host header"}`, WS 403 "Host not allowed". Using the Tailscale IP, as we do, passes by default.
- **Token form:** only `Authorization: Bearer …`. `X-API-Key` is not read (matches Noa's note). Never put the password in a URL on shared hosts; `tcp://…?password=` leaks into process lists.
- **Proxy:** the daemon is on the tailnet, the box's tailscaled is userspace. Use `curl -x http://localhost:1056 …` (HTTP CONNECT) or `--socks5-hostname localhost:1055`. Node: `https-proxy-agent` with `ws` (works for `ws://`), or undici `ProxyAgent` for fetch. See Tailscale on the box and Paseo control (both deleted project notes).
- **Binding:** neko-sphere binds `0.0.0.0:6767` (all interfaces) with a password. Docs warn against `0.0.0.0` without a password.
- **Version skew:** CLI 0.11.2 talked to daemon 0.11.0-beta.5 fine. Older hosts return "update host" errors for newer capabilities. Check `features` in the status frame.
- **Providers not found:** the daemon runs under systemd/Nix with a stripped PATH (`/nix/store/…-system-path/bin` etc.). `paseo provider diagnostic <p>` shows `Resolved path: not found`. Fix by adding the CLI to the daemon's PATH or `agents.providers.<id>.command=[abs path]` then `paseo reload`. Related flake note: [[Projects/Flake]] (standalone Paseo daemon on box, `docs/paseo-daemon.md`).
- **Long runs:** `paseo run` waits forever by default (`--wait-timeout`), `paseo wait --timeout`, SDK `waitForFinish` 10 min, MCP `send_agent_prompt` returns on dispatch. Pi control RPCs default to 60 s (`params.rpcTimeoutMs`). A timeout never cancels the agent.
- **kill/archive semantics are loose** (issue #5121, open): on 0.8.0 `kill_agent` did not stay terminal and a prompt to an archived agent un-archived it. Use `cancel_agent` / `paseo stop` for interrupts and verify state with `get_agent_status`.
- **Other open issues worth knowing:** #5163 `send_agent_prompt` from an agent cancels the target's running turn and kills its subagents; #3248 agent-scoped background `paseo run` may never notify the parent; #5951 agent stuck "running" with no live runtime; #5318 `paseo start` reports `already_running` with null listen while starting; #5127 CLI `ssh://` transport can time out; #3004 Pi MCP adapter registration race.
- **#690 (closed 2026-06-12):** with password auth the injected `/mcp/agents` client once got 401 (it sent no bearer). Current code authorizes injected agents with a per-run capability token (or the password); I did not verify that this was the fix.

## 9. Pi MCP question (Noa, 2026-10-03)

- Pi 0.99+ ships MCP built in (extension command `mcp`, `sourceInfo.path: "builtin:mcp"`). Paseo ≤ 0.10.2 only recognised the open-source `pi-mcp-adapter` and returned `supportsMcpServers:false` otherwise, so Pi agents started with no Paseo MCP (no `create_agent` etc.). Issue **#5744**.
- Fix **PR #5762** (merged 2026-09-30 14:08 UTC) registers Paseo's servers through `pi.registerMcpServer` in the per-session extension Paseo already loads. Limits: stdio and streamable HTTP only (SSE and names outside `[A-Za-z0-9_-]` fail agent creation); a same-named server in Pi's `mcp.json` wins; tool exposure uses Pi's default (`codemode`). Sessions with `pi-mcp-adapter` keep the `--mcp-config` path. Shipped in 0.11.0 (10-07); the neko-sphere daemon 0.11.0-beta.5 (10-05) is later than the merge, so it should contain it (not tested, no Pi installed there).
- Related still-open: #3004 (adapter command-registration race), #1892 (voice without `speak` tool when adapter missing). 0.9.2 had "Pi keeps your existing MCP tools and settings when Paseo adds its own".
- Also remember Paseo tool injection is off by default (`daemon.mcp.injectIntoAgents`).

## 10. Orchestration and nstack-as-plugin (short)

- **Fan-out recipe (CLI):** `id=$(paseo run --no-wait -q --title "issue-412" --provider <p/m> --new-workspace worktree --worktree-mode branch-off --new-branch nstack/412 --base origin/main --label issue=412 "<brief>")`; later `paseo send "$id" "<bounce feedback>"` (same session), `paseo wait "$id" --timeout N`, `paseo logs "$id" --tail 20 --json`, `paseo archive "$id"`. `--label` lets an orchestrator re-find workers (`paseo ls --label issue=412 --json`; SDK `agents.list({filter:{labels}})`). The same via SDK/MCP; MCP workers get `notifyOnFinish`.
- **Fit with nstack:** one-worker-per-issue-in-a-worktree, bounce follow-ups into the same session, and `--output-schema` for structured reviewer verdicts all exist natively. Missing: durable job table / idempotent claim by GitHub event, lease/reconcile, retry policy. Those stay with a dispatcher (see [[2026-10-09 Self-hosted GitHub agent dispatch]]).
- **Plugin system (0.11):** `paseo plugin init|add|install`; TypeScript, `index.server.ts` runs in a daemon subprocess (hooks `server.on(...)`/`server.before(...)`, RPCs), `index.client.tsx` adds screens/panels/slash commands on every client. Hooks: `agent.created`, `agent.closed`, `agent.turn_started`, `agent.turn_ended {outcome,timeline}`, `agent.permission_requested/resolved`, `agent.archived`, `workspace.created/archived`; actions: send follow-up when a turn ends, answer permissions, inject MCP servers/env, choose worktree isolation (`plugin-examples/lifecycle-actions`). Plugins can use the SDK against the host. Trusted, unsandboxed code. A plugin can add its own provider.
- **Hub alternative:** `.paseo/triggers/*.yml`, `paseo hub deploy`; GitHub events include `github.issue_created`, `issue_comment_created`, `issue_label_added`, `pull_request_created`, `pull_request_label_added`, `push`, review events; `from_users` allowlist required. Hub-run unattended agents accept **Claude, Codex, OpenCode only** (no Pi/OMP). An assigned-issue event was not seen in the docs I read (unverified).
- **Limits to design around:** daemon state is local JSON files, no multi-daemon scheduler; schedules always start a *new* agent per run; heartbeat only prompts the caller; kill/archive leak (#5121); one maintainer and 1154 open issues, so pin versions.
