# Two binaries: papagod and papago

Decision: one Go module ships two binaries. `papagod` is the Daemon — pure Go, no UI dependencies, the artifact the systemd user unit and headless hosts run. `papago` is the GUI plus the CLI client subcommands (ls/run/send/wait/logs/stop, daemon status), built with `mygo build` for desktop machines. Constraint: the CLI paths inside `papago` must never load the GTK stack; MyGo opens its native libraries lazily through purego, so importing the UI packages is expected to be inert until a window is created — verify with a spike before relying on it, and move the CLI subcommands into `papagod` if the import alone loads libraries. Rationale: a daemon that lives under systemd and on headless boxes should not carry a GUI toolkit, while desktop users still get one artifact for GUI and scripting.
